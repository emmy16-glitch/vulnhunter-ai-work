# VulnHunter Dependency-Ordered Roadmap

**Status:** Binding delivery order  
**Rule:** complete active bounded work and earlier mandatory programmes before beginning later programmes  
**Current date:** 2026-08-02

## 0. Roadmap rules

- Re-check `main`, open pull requests, CI, review threads and recent merges before every implementation sequence.
- Finish a real active bounded implementation pull request before starting unrelated later work.
- Do not repeat merged work.
- Do not classify documentation as implementation.
- Implement one bounded dependency-ordered pull request at a time.
- Preserve deterministic authority, private-target restrictions, review independence and publication separation.
- Never weaken quality gates merely to advance the roadmap.
- Record genuine blockers separately from planned work.

The mandatory product sequence is:

```text
Programme 1 — AI-first assessment workspace
    -> Programme 2 — Premium interaction, motion and conversation
        -> Programme 3 — ML and Hugging Face production architecture
            -> remaining scanner, isolation and production-readiness milestones
```

These controls establish workflow integrity. They do not establish that a sufficiently diverse real dataset already exists.

## 3. Completed foundation — Local ML and advisory-provider plumbing

- deterministic reviewed-observation dataset construction;
- deterministic dataset hashes and private JSONL export;
- duplicate/conflict readiness gates;
- complete-scan grouped splitting;
- training-only grouped model selection;

- explicit model allowlists;
- bounded structured advisory output;

- deterministic fallback and safe abstention.

These foundations prove software plumbing and governance boundaries. They do not establish production vulnerability-classifier performance.

## 4. Completed foundation — Controlled scanner harness and protocol

- scanner-manager and worker responsibilities are separated;
- scanner protocol `1.0` defines shared Nuclei, OpenVAS and mobile contracts;
- Nuclei has a controlled lifecycle, bounded evidence, cancellation, timeout and recovery;
- version/feed/checksum compatibility is centrally tracked;

- public scanning, unrestricted execution and exploit automation remain unavailable.

# After mandatory programmes — Scanner and production hardening

These items remain important but must be sequenced against the actual completed state rather than used to interrupt active mandatory work.

## Scanner milestones

1. Authenticate manager-to-worker transport without exposing secrets or raw commands.
2. Sign and attest worker images and compatibility manifests.
3. Populate and review the Nuclei template trust registry.
4. Harden the real unprivileged Nuclei launcher for authorised disposable private labs.
5. Expand DNS, redirects, cancellation, timeout, redaction, process cleanup and recovery acceptance.
6. Implement OpenVAS and mobile adapters only after versions, feeds, isolation and approval policies are selected.
7. Keep public scanning and unrestricted intrusive execution prohibited.

## Artifact authenticity and isolation

- cryptographically sign or attest campaign releases, authorization snapshots, review attestations, model artifacts and experiment evidence;
- protected key storage, rotation, revocation and verification;
- dedicated low-privilege container/VM/OS sandbox for verifiers, workers and candidate worktrees;
- formal schema migration, backup, restore, retention and disaster recovery;
- reproducible versioned packages and releases;
- production deployment acceptance for TLS, proxy headers, database, workers, logging, monitoring, rollback and incident response.

## Dataset acquisition remains a real-world dependency

- select intentionally diverse owned/authorised local applications;
- issue narrow authorisations and governed campaigns;
- collect only through approved bounded paths;
- assign two independent reviewers and adjudicate disputes;
- freeze release only after integrity/diversity gates;
- preserve application-family metadata;
- keep external families untouched;
- publish honest calibration, generalisation and error reports.

No architecture or automation can fabricate this real evidence.

# Explicitly deferred or prohibited

- exploitation or credential attacks;
- arbitrary public-Internet scanning;
- unrestricted dynamic execution;
- autonomous campaign approval, review, adjudication or release;
- autonomous model promotion or activation;
- automatic retraining from drift;
- model-written authoritative labels;
- model-granted scope or approval;
- unreviewed Hugging Face remote custom code;
- remote private/source embeddings without exact policy and approval;
- outer-loop executable code injection;
- automatic merge, deployment or publication from advisory output;
- production performance claims from synthetic, leaked or insufficiently diverse data;
- replacing the deterministic baseline solely because a larger model exists.

# Permanent roadmap invariants

- backend and persisted state remain authoritative;
- human review remains label authority;
- earlier mandatory programmes finish first;
- active bounded pull requests are not abandoned;
- production training consumes governed releases;
- external evaluation isolates application families;
- raw score is not calibrated confidence;
- unfamiliar inputs may abstain;
- active models are registry-backed and rollback-capable;
- shadow models do not affect users;
- drift does not grant retraining authority;
- Hugging Face models/tokenizers are revision-pinned for approved use;
- retrieved content is untrusted;
- models receive no operational tools through advisory routes;
- all optional AI can be disabled without breaking core operation;
- every programme is complete only when code, tests, evidence and current-state documentation agree.
